Streams: the Python SDK user's code, Moe (Jetty) vs Dan

Scope: the code a user writes to configure workers and clients, publish from activities and workflows, and consume in a UI backend. Workflow reads and suspend-and-notify are left out. Dan: sdk-python 098a10df (superproject 2026/10/ai198-streams-dan), package temporalio.streams. Moe: Jetty sdk-python bbbadf0a (branch moe/jetty/v2/j5-direct-reads), package temporalio.contrib.streams; compared against Brook a6ff7beb. Moe's READMEs read as AI-written; claims taken from them are marked as such.

Findings

  • Moe's Jetty Python API is Brook's plus additions. Brook a6ff7beb is an ancestor of Jetty bbbadf0a; the seven Brook example programs are byte-identical in Jetty. Jetty adds NativeStreamPlugin, subscribe in workflow code, and more than one Stream plugin per Worker. The one user-visible difference: a Brook Worker accepts only one Stream plugin (ValueError "The Worker has another extension"). Nothing a Brook user writes breaks at Jetty.
  • Native is opt-in in Moe's design, and the default in Dan's. Moe: a client or Worker with no Stream plugin raises StreamConfigError; native needs plugins=[NativeStreamPlugin()]. Dan: every client has the native backend and it is the default; Redis is an added backend. So Dan's design matches "streams work with no external service; Redis is an optional drop-in"; Moe's Jetty docs would instead say "add a Stream plugin: Redis or native".
  • In both, the backend is a property of each stream, recorded in its handle, and chosen from the default at create time. Neither is a transparent drop-in at the level of a running workflow. Moe's Jetty README says a change of the default "changes the commands of replayed creates" and prescribes workflow.patched (README). In Dan's, workflow stream writes are not commands, so there is no nondeterminism error, but a running workflow whose default changes would write later records to the other backend. I have not tested that case in Dan's.
  • Workflow publish works differently. Moe: each create_stream, publish and close in workflow code is one Local Activity (a marker in History), on Redis and on native. Dan: the worker appends at the end of the activation and adds nothing to History; a store failure fails the workflow task.
  • Typing. Moe: a @streams.defn class declares the stream name and each topic's type, and handles are generic in it. Dan: streams are identified by string names and handles are untyped; a type is given per topic (topic("turns", type=Turn)) or per read.
  • Where streams can live. At Jetty, Moe's native server supports standalone streams and workflow-embedded streams (targetOf). Neither of Moe's stages has Standalone-Activity-embedded streams. Dan's has all three.

1. Configure the client and the workers

In both, stream configuration lives on the client, and a Worker built from the client inherits it. Neither needs stream-specific worker arguments. Dan's is a client config field, stream_backends, because streams are built into the SDK; Moe's is a plugin because his streams machinery (interceptors, Local Activities, Core extension) only exists when a plugin installs it.

2. Declare the stream

Moe
from temporalio.contrib import streams

@dataclass
class Turn:
    kind: str
    text: str = ""

@streams.defn(name="events")
class Events:
    turns = streams.topic(Turn)
    tokens = streams.topic(str)

# Another stream with the same topics:
Turn3 = streams.with_name(Events, "turn-3")
Dan
# Nothing to declare. A stream is identified by a string name,
# and a type is given per topic where it is used.

@dataclass
class Turn:
    kind: str
    text: str = ""

What @streams.defn(name=...) does in Moe's (_defn.py):

  • It collects the class's streams.topic(T) attributes, including inherited ones, checks that topic names are unique, and attaches a StreamDefinition(name, topics) to the class. name defaults to the class name. It registers nothing with a worker or client, and the class has no methods to implement.
  • The name is the stream's identity. create_stream(Events) in a workflow creates the stream with ID <workflow id>:<first run id>:events. StreamClient(client).workflow_stream(handle, Events) computes the same ID from the workflow handle, with no call to the server. with_name makes a subclass with the same topics under another name, so one workflow can have several streams of one definition.
  • The topics are a typed contract shared by writers and readers. Handles are generic in the definition, so stream.topic(Events.turns) is a topic of Turn for the type checker, and a read decodes each topic's values as its declared type. A topic name not in the definition raises unless type= is given.
  • The definition does not travel with a handle. A handle serializes as its ID, owner and backend, and the receiving parameter's type (for example ActivityStream[Events]) provides the definition again.

Compared with the SDK's other defn decorators: like @workflow.defn and @activity.defn, it fixes a name that both sides use (there, the workflow or activity type on the wire; here, part of the stream ID) and gives callers a typed reference, as client.start_workflow(Agent.run, ...) uses the workflow class. Unlike them, it has no implementation and is not registered with a worker. It is a schema, closer to a Nexus @nexusrpc.service interface definition than to @workflow.defn.

from temporalio import workflow
from temporalio.contrib import streams
from temporalio.contrib.streams import workflow as stream_workflow

@dataclass
class CallModelInput:
    prompt: str
    stream: streams.ActivityStream[Events]

@workflow.defn
class Agent:
    @workflow.run
    async def run(self, prompt: str) -> str:
        # Created on the worker's default backend: Redis.
        stream = await stream_workflow.create_stream(Events)
        turns = stream.topic(Events.turns)

        await turns.publish(Turn("model"))   # returns the offset

        reply = await workflow.execute_activity(
            call_model,
            # The parameter's type picks the handle class.
            CallModelInput(prompt, streams.ActivityStream.from_handle(stream)),
            start_to_close_timeout=timedelta(minutes=5),
        )
        await turns.publish(Turn("done", reply))
        return reply
        # close_with_run=True by default: closes with the run chain.
Dan
from temporalio import workflow

@workflow.defn
class Agent:
    @workflow.run
    async def run(self, prompt: str) -> str:
        # Created on the worker's default backend: Redis.
        events = await workflow.create_stream("events")
        turns = events.topic("turns", type=Turn)

        await turns.publish(Turn("model"))   # returns None

            start_to_close_timeout=timedelta(minutes=5),
        )
        await turns.publish(Turn("done", reply))
        return reply
        # The stream closes when the run ends (native: server;
        # Redis: worker, after the server accepts the completion).

4. Activity: publish

Moe
from temporalio import activity
from temporalio.contrib import streams

@activity.defn
async def call_model(input: CallModelInput) -> str:
    tokens = input.stream.topic(Events.tokens)
    await tokens.publish("first")            # one append, returns offset

    async with streams.BufferedPublisher(
        tokens, max_delay=timedelta(milliseconds=100)
    ) as buf:                                # timer flushes; exit flushes
        async for chunk in llm(input.prompt):
            buf.publish(chunk)
    return "..."

# Sync activity in a thread pool: type the field as
#   streams.SyncActivityStream[Events]; publish() blocks.
Dan
from temporalio import activity
from temporalio.streams import StreamHandleBase

@activity.defn
async def call_model(events: StreamHandleBase, prompt: str) -> str:
    stream = activity.get_stream_handle(events)
    tokens = stream.topic("tokens", type=str)
    await tokens.publish("first")            # one append, awaited

    async with stream.buffered() as buf:     # exit awaits flush()
        async for chunk in llm(prompt):
            buf.publish(chunk, topic="tokens")   # memory only
            await buf.flush()                    # user decides when
    return "..."

# Sync activity in a thread pool:
#   activity.get_sync_stream_handle(events).publish("x", topic="tokens")

Dan's BufferedStreamWriter has no timer; records still buffered when the attempt ends are lost. Moe's BufferedPublisher flushes on max_delay, and the plugin flushes it at the end of the attempt. In both, the activity gets the stream only from a handle passed in its input.

5. UI backend: configure the client

Same as step 1: the UI backend's client needs the same backends as the workers, so that a handle's backend name resolves. In Moe's design a client with no Stream plugin cannot read even a native stream; in Dan's it reads native streams with no config.

6. UI backend: consume

Moe
from temporalio.contrib import streams

handle = await client.start_workflow(
    Agent.run, "hi", id="agent-1", task_queue="agent"
)
# The client's default backend: Redis.
stream = streams.StreamClient(client).workflow_stream(handle, Events)

async for item in stream.subscribe(          # waits by default
    Events.turns, Events.tokens,
    create_wait=timedelta(seconds=10),       # stream may not exist yet
):
    if isinstance(item, streams.Superseded):
        unrender_where(item.withdraws)
    elif isinstance(item, streams.Closed):
        done(item.result, item.failure)      # last item
    else:
        render(item.topic, item.data)        # item.offset resumes

# One topic:
stream.topic(Events.turns).subscribe(from_offset=saved_offset + 1)
Dan
from temporalio.streams import Withdrawal

handle = await client.start_workflow(
    Agent.run, "hi", id="agent-1", task_queue="agent"
)
# The client's default backend: Redis.
stream = handle.stream("events")

records = stream.fetch_records(wait_new_records=True)  # default False
async for r in records:
    if isinstance(r, Withdrawal):
        unrender(r.cursor)
    else:
        render(r.topic, r.value, r.status)   # r.cursor resumes
# Ends at the close:
records.close    # StreamClose(status, failure, reason)

# One topic, typed:
stream.topic("turns", type=Turn).fetch_records(after=saved_cursor)
